# Pricing & Cost Policy

## 1. 목적

이 문서는 AI Ops Platform MVP의 가격표 구조, 비용 계산 기준, 표시 단위, 정산 해석 기준을 정의한다.

이 문서가 필요한 이유는 다음과 같다.

- Gateway, Billing, UI가 서로 다른 비용 기준을 사용하면 신뢰를 잃는다.
- 병렬 개발 시 가장 쉽게 어긋나는 영역이 가격표와 계산 규칙이다.
- 비용 추천 기능은 정확한 원가/표시 비용 기준 위에서만 의미가 있다.

## 2. 핵심 원칙

1. 비용 계산의 단일 기준은 Billing이 가진 가격표다.
2. Gateway는 비용을 추정할 수 있어도 최종 비용 소유자는 Billing이다.
3. UI는 Billing이 계산한 비용을 표시 기준으로 사용한다.
4. 가격표 버전은 변경 이력을 남겨야 한다.
5. 원가와 표시 가격을 구분한다.

## 3. 비용 모델 범위

MVP는 아래 세 가지 모델만 지원한다.

| 모델 | 설명 | 예시 |
|------|------|------|
| `per_token` | 토큰당 과금 | LLM 요청 |
| `per_request` | 호출당 고정 비용 | 단순 OCR API |
| `fixed` | 월/기능 고정 비용 | 내부 사내 서비스 |

초기 우선순위는 `per_token`이다.

## 4. 가격표 구조

## 4.1 가격표 기본 필드

| 필드 | 설명 |
|------|------|
| `price_table_version` | 가격표 버전 |
| `service_id` | 서비스 식별자 |
| `model` | 모델명 |
| `pricing_model` | 과금 유형 |
| `currency` | 통화 |
| `unit_price_input` | 입력 토큰 단가 |
| `unit_price_output` | 출력 토큰 단가 |
| `unit_price_request` | 요청당 단가 |
| `effective_from` | 적용 시작 시각 |
| `effective_to` | 적용 종료 시각 |
| `status` | active/inactive |

## 4.2 샘플 가격표

```json
{
  "price_table_version": "2026-03-v1",
  "service_id": "svc_doc_summary",
  "model": "gpt-4o-mini",
  "pricing_model": "per_token",
  "currency": "KRW",
  "unit_price_input": 0.08,
  "unit_price_output": 0.32,
  "unit_price_request": 0,
  "effective_from": "2026-03-01T00:00:00Z",
  "effective_to": null,
  "status": "active"
}
```

## 5. 비용 계산 기준

## 5.1 per_token 계산식

```text
총비용 = (prompt_tokens × 입력단가) + (completion_tokens × 출력단가)
```

예시

- `prompt_tokens = 900`
- `completion_tokens = 320`
- `input_price = 0.08 KRW`
- `output_price = 0.32 KRW`

계산

```text
(900 × 0.08) + (320 × 0.32) = 72 + 102.4 = 174.4 KRW
```

## 5.2 per_request 계산식

```text
총비용 = 요청 수 × 요청당 단가
```

## 5.3 fixed 계산식

MVP에서는 월별 정산이 아니라 조회용 참조값으로만 사용한다.

## 6. 소수점과 반올림 규칙

- 내부 계산은 최소 소수점 4자리 이상 유지
- 저장 시 `decimal` 사용
- 사용자 표시 시 기본 소수점 2자리 반올림
- 팀/월 집계는 합산 후 반올림

반올림 순서가 다르면 총합이 달라질 수 있으므로, 개별 건 표시용 반올림과 집계 저장용 반올림을 분리한다.

## 7. 통화 기준

MVP 기본 통화는 `KRW`다.

원칙

- 원본 벤더 가격이 USD여도 Billing 내부 표준 통화를 `KRW`로 환산해 저장할 수 있다.
- 환율을 적용한다면 적용 시각과 환율 버전을 기록한다.
- MVP에서는 환율 자동 변동보다 운영자가 관리하는 기준 환율 테이블을 권장한다.

## 8. 비용 계산 시점

최종 비용 계산 시점은 `usage.tracked` 수신 이후다.

이유

- prompt/completion token이 완료 후 확정되는 경우가 많다.
- 실패한 요청과 부분 성공 요청의 처리 기준을 분리해야 한다.

흐름

1. Gateway가 `ai.requested` 발행
2. Usage가 정규화된 `usage.tracked` 이벤트 발행
3. Billing이 가격표 조회
4. Billing이 비용 계산
5. `cost.calculated` 이벤트 발행

## 9. 실패 요청 비용 정책

MVP 권장 정책은 아래와 같다.

| 상태 | 비용 처리 |
|------|-----------|
| 요청 전 차단 | 비용 0 |
| 외부 AI 호출 전 실패 | 비용 0 |
| 외부 AI 호출 후 실패, 토큰 정보 없음 | 비용 미확정 또는 0, 운영 규칙 필요 |
| 외부 AI 호출 후 실패, 토큰 정보 있음 | 실제 사용량 기준 비용 계산 가능 |

실무상 중요한 점

- `FAILED`라고 해서 항상 비용 0은 아니다.
- 외부 벤더가 이미 토큰을 소비했다면 비용은 발생할 수 있다.
- 따라서 `status`와 `billable` 여부를 분리하는 것이 바람직하다.

## 10. 권장 비용 레코드 필드

기존 `billing_records`에 아래 필드를 추가 고려한다.

| 필드 | 설명 |
|------|------|
| `price_table_version` | 어떤 가격표를 썼는지 |
| `billable` | 청구 가능 여부 |
| `input_unit_price` | 입력 단가 |
| `output_unit_price` | 출력 단가 |
| `cost_before_rounding` | 반올림 전 원값 |
| `exchange_rate_version` | 환율 버전 |

## 11. UI 표시 기준

## 11.1 A가 따라야 할 규칙

- 비용은 Billing API가 내려준 값을 그대로 표시한다.
- UI 자체 계산값을 최종값처럼 보여주지 않는다.
- 추정 비용과 확정 비용을 구분한다.

표시 예시

- `예상 비용`: 실행 전 또는 직후 추정치
- `확정 비용`: Billing 계산 완료 후 값

## 11.2 사용자 커뮤니케이션

비용이 아직 계산 중이면 아래와 같은 상태를 허용한다.

- `계산 중`
- `반영 대기`
- `최신 비용 집계 중`

## 12. 가격표 운영 규칙

## 12.1 변경 원칙

- 가격표는 임의 수정이 아니라 버전 추가 방식으로 관리한다.
- 과거 실행 이력은 당시 적용 버전을 유지한다.
- 동일한 `service_id`, `model` 조합이라도 기간별 단가가 달라질 수 있다.

## 12.2 변경 절차

1. 새 가격표 초안 작성
2. C 검토
3. B가 Gateway 추정 로직 영향 확인
4. A가 UI 표시 영향 확인
5. dev/staging 검증
6. 적용 시각 이후 활성화

## 13. 비용 이상 탐지 기준

MVP에서 아래 이상 징후를 알림 대상으로 본다.

- 팀 일비용이 최근 7일 평균 대비 2배 초과
- 특정 모델 비용 급증
- 가격표 미매핑 건 발생
- `cost.calculated` 실패율 증가
- 0원 처리 비율 비정상 급증

## 14. 추천 기능과의 관계

Recommendation은 아래 입력을 사용한다.

- 서비스별 평균 비용
- 팀별 고비용 패턴
- 대체 모델 후보와 단가 차이
- 성공률/지연과 비용의 균형

추천 메시지는 비용 정보의 출처를 Billing으로 간주해야 한다.

예시

`최근 7일 동안 문서 요약 작업의 평균 비용이 증가했습니다. 동일 유형 작업에 대해 gpt-4.1-mini 대체를 검토하세요.`

## 15. 역할별 책임

## 15.1 A

- 확정 비용과 추정 비용 UX 구분
- 비용 지연 상태 표시
- 팀/사용자 비용 화면에서 집계 단위 일관성 유지

## 15.2 B

- 실행 메타데이터를 Billing이 계산 가능한 수준으로 보장
- `request_id`, `service_id`, `model`, 토큰 정보 전파
- 정책 차단과 비용 발생 실패를 구분

## 15.3 C

- 가격표의 단일 소유자
- 계산식과 반올림 규칙 구현
- 비용 집계와 추천 입력 정합성 보장

## 16. 샘플 테스트 케이스

### 케이스 1: 정상 토큰 과금

입력

- `prompt_tokens=1000`
- `completion_tokens=500`
- 입력단가 `0.1`
- 출력단가 `0.3`

기대 결과

- 총비용 `250.0`

### 케이스 2: 정책 차단

입력

- Gateway에서 사전 차단

기대 결과

- 비용 `0`
- `billable=false`

### 케이스 3: 가격표 누락

입력

- `model`에 대한 단가 정보 없음

기대 결과

- 비용 계산 실패 기록
- 알림 발생
- 사용자 화면에는 `계산 지연` 또는 `확인 필요` 표시

## 17. 체크리스트

개발 시작 전

- 가격표 필드 합의
- 통화 기준 확정
- 반올림 규칙 합의
- 실패 요청 비용 정책 합의

통합 전

- 샘플 가격표 테스트
- UI 표시 값과 Billing 값 일치 확인
- 가격표 누락 알림 테스트
- 추천 비용 데이터 연동 확인
