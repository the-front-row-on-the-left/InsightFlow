# Development Guide For A Platform

## 1. 역할 정의

A의 역할은 사용자 입장에서 가장 먼저 보이는 플랫폼 경험을 만드는 것이다.

핵심 책임

- 서비스 카탈로그 조회 UX
- 단일 실행 UX
- Workflow 생성/저장 UX
- 실행 결과 조회 UX
- 비용/추천 요약 화면 연결

세부 설계 기준은 [13_AI_Platform_Spec.md](/Users/skax/Downloads/ai_ops_docs_bundle/13_AI_Platform_Spec.md)를 우선 따른다.

## 2. A의 목표

A의 목표는 "예쁜 화면"보다 "실행 가능한 사용자 흐름"이다.

초기 MVP에서 반드시 살아 있어야 하는 흐름

1. 서비스 목록을 본다.
2. 하나를 선택해 실행한다.
3. 실행 상태와 결과를 본다.
4. 최소한의 Workflow를 저장하거나 조회한다.
5. 비용/추천 요약을 본다.

## 3. A가 처음 2~3일 안에 해야 할 일

1. 화면 정보 구조를 고정한다.
2. mock API 응답을 기준으로 화면 skeleton을 만든다.
3. 카탈로그, 실행, 결과 조회 3개 화면을 우선 연결한다.
4. 공통 API client와 에러 처리 구조를 만든다.
5. `request_id`를 화면 상태에 보존하는 방식을 정한다.

초반에는 완성도보다 연결 가능한 골격이 더 중요하다.

## 4. 권장 화면 구현 순서

### 1순위

- 서비스 목록
- 서비스 상세
- 실행 화면
- 실행 결과 조회

### 2순위

- Workflow 생성
- Workflow 저장/조회

### 3순위

- 비용 요약
- 추천 요약

이 순서를 지키면 B, C와의 연동 의존성을 늦추면서도 데모 가능한 흐름을 빨리 만들 수 있다.

## 5. 화면별 핵심 포인트

## 5.1 서비스 목록

반드시 보여야 할 필드

- `service_id`
- `name`
- `category`
- `pricing_model`
- 추천 뱃지 존재 여부

주의사항

- 정렬/필터는 과하게 복잡하게 시작하지 않는다.
- 카드 수집형 UI보다 "실행으로 이어지는 탐색"이 중요하다.

## 5.2 서비스 상세

반드시 보여야 할 것

- 서비스 설명
- 지원 모델
- 비용 모델
- 실행 진입 버튼

주의사항

- 비용은 추정/모델 수준 안내로 시작하고, 최종 확정 비용은 Billing 기준으로 본다.

## 5.3 실행 화면

반드시 처리할 것

- 입력값 제출
- 실행 중 상태 표시
- 성공/실패 구분
- `request_id` 표시 또는 내부 보관

실패 시 보여줄 구분

- `POLICY_BLOCKED`
- `RATE_LIMIT_EXCEEDED`
- 일반 실행 실패

## 5.4 실행 결과 화면

반드시 처리할 것

- 실행 상태
- 결과 payload
- `request_id`
- 비용 반영 상태

비용은 아래처럼 상태를 나눈다.

- 계산 전
- 계산 중
- 계산 완료

## 5.5 Workflow 화면

초기 목표

- 2단계 이상 서비스 조합 저장
- drag-and-drop 없이 리스트 기반 구성
- 단계별 `service_id` 관리

실수하기 쉬운 지점

- 프론트 고유 구조를 백엔드 계약보다 먼저 고정하는 것
- step 구조에 임시 필드를 많이 넣는 것

## 6. 데이터/상태 관리 가이드

상태는 크게 나누면 아래 4종류다.

- 카탈로그 조회 상태
- 실행 요청 상태
- 실행 결과 조회 상태
- Workflow 편집 상태

권장 원칙

- 서버 데이터와 폼 편집 상태를 분리한다.
- API 응답 타입과 화면 ViewModel 변환층을 분리한다.
- mock 응답과 real 응답이 섞이지 않게 adapter를 둔다.

## 7. API 연동 가이드

초기에 바로 필요한 API

- `GET /api/catalog/services`
- `GET /api/catalog/services/{service_id}`
- `POST /api/executions`
- `GET /api/executions/{execution_id}`
- `POST /api/workflows`
- `GET /api/workflows/{workflow_id}`

연동 순서

1. mock 응답으로 UI 완성
2. B의 실제 API와 연동
3. C의 조회 API와 연동

## 8. A가 B와 맞춰야 할 것

- `POST /api/executions` 요청 바디
- 공통 에러 응답 구조
- `request_id` 반환 위치
- 더미 사용자/팀 컨텍스트 방식
- 실행 상태 표현값

특히 `execution_id`, `request_id`, `status` 값은 UI 라우팅과 화면 상태에 직접 영향이 크다.

## 9. A가 C와 맞춰야 할 것

- 비용 조회 API 응답 구조
- 추천 조회 API 응답 구조
- 확정 비용과 추정 비용 구분
- 빈 추천 결과 처리

주의사항

- 비용은 UI에서 계산하지 않는다.
- 추천이 아직 없을 수 있다는 전제를 UX에 반영한다.

## 10. 에러 처리 기준

화면에서 구분해야 하는 대표 에러

- 잘못된 입력
- 정책 차단
- 요청 제한 초과
- 일시적 서버 오류
- 비용 계산 지연

권장 UX

- 사용자 행동으로 고칠 수 있는 것은 안내 문구를 구체적으로
- 사용자가 고칠 수 없는 것은 `request_id` 기반 문의 가능 상태로

## 11. 로깅과 디버깅

A는 아래를 남기면 디버깅이 쉬워진다.

- 현재 라우트
- 호출 API
- 응답 `request_id`
- 에러 `code`
- 사용자 액션 시점

단, 민감한 입력 원문 전체를 프론트 로그에 남기지 않는다.

## 12. 테스트 가이드

최소 테스트 범위

- 서비스 목록 렌더링
- 실행 요청 폼 제출
- 정책 차단 메시지 노출
- 실행 결과 상태 렌더링
- 비용/추천 빈 상태 처리

권장 시나리오

1. 카탈로그 진입
2. 서비스 선택
3. 실행 요청
4. 실패/성공 상태 확인
5. 결과 조회

## 13. PR 기준

- 화면이 아니라 흐름 단위로 PR을 나눈다.
- mock 제거와 실API 연결을 분리하면 리뷰가 쉽다.
- 스크린샷만 말고 샘플 요청/응답 기준도 설명한다.

좋은 PR 예시

- `feat(platform): add service catalog list with mock adapter`
- `feat(platform): integrate execution detail page with gateway API`

## 14. A가 자주 막히는 지점과 해결법

문제

- B API가 아직 준비되지 않음

해결

- mock adapter를 먼저 만들고 API 타입만 고정

문제

- C 비용 API가 늦음

해결

- 비용 상태 placeholder를 먼저 구현

문제

- 실행 결과 payload 구조가 자주 바뀜

해결

- 결과 렌더러를 느슨한 구조로 두고 raw payload viewer를 임시 허용

## 15. 완료 기준

- 카탈로그 조회가 된다.
- 실행 요청과 결과 조회가 된다.
- 정책 차단과 일반 실패를 구분해 보여준다.
- Workflow 저장/조회 기본 흐름이 있다.
- 비용 또는 추천 화면 최소 1개가 연결된다.
