# Incident Response Runbook

## 1. 목적

이 문서는 AI Ops Platform MVP 운영 중 장애 또는 이상 상황이 발생했을 때 탐지, 분류, 대응, 복구, 사후 기록 방법을 정의한다.

핵심 목표는 다음과 같다.

- 누가 무엇을 먼저 봐야 하는지 즉시 알 수 있게 한다.
- A, B, C의 책임 경계를 유지하면서도 공조가 가능하게 한다.
- 장애 중 커뮤니케이션 공백과 중복 대응을 줄인다.

## 2. 장애 등급

| 등급 | 기준 | 예시 |
|------|------|------|
| Sev-1 | 핵심 기능 전면 불가 | 전체 실행 실패, Gateway 전면 장애 |
| Sev-2 | 일부 핵심 기능 불안정 | 비용 반영 지연, 정책 오판단 증가 |
| Sev-3 | 우회 가능, 기능 일부 영향 | 추천 생성 실패, 일부 화면 에러 |

## 3. 공통 대응 원칙

1. 추측보다 사실 기반으로 판단한다.
2. 첫 10분은 원인 확정보다 영향 범위 파악에 집중한다.
3. 장애 대응 중 계약 변경이나 구조 변경은 하지 않는다.
4. 수동 조치가 필요하면 반드시 기록한다.
5. 장애 종료 후 사후 회고를 남긴다.

## 4. 기본 역할

| 역할 | 기본 담당 | 책임 |
|------|-----------|------|
| Incident Lead | 기본적으로 B, 필요시 교대 | 상황 정리, 우선순위 결정, 커뮤니케이션 |
| UI/사용자 영향 담당 | A | 사용자 증상 확인, 우회 방법 안내 |
| Control Plane 담당 | B | Gateway, Policy, 추후 인증 확장 지점, RateLimit 확인 |
| Data Plane 담당 | C | Usage, Billing, Recommendation, Kafka 확인 |
| Recorder | 상황에 따라 지정 | 타임라인, 조치, 판단 근거 기록 |

초기 MVP에서는 B가 Incident Lead를 맡는 것을 권장한다. 모든 요청이 Gateway를 통과하므로 가장 먼저 영향 범위를 좁히기 쉽기 때문이다.

## 5. 장애 대응 공통 절차

## 5.1 탐지

장애는 다음 경로로 탐지될 수 있다.

- 알림 시스템
- 내부 데모/QA
- 사용자 제보
- 대시보드 이상 징후

## 5.2 초기 확인

5분 안에 아래를 확인한다.

- 현재 영향 기능
- 영향 사용자 범위
- 최초 발생 시각
- 최근 배포 여부
- 공통 에러 코드

## 5.3 분류

아래 질문으로 분류한다.

- 전체 실행이 안 되는가
- Gateway 진입, 정책, 제한 중 어느 지점에서 실패하는가
- 정책/제한이 과도하게 차단하는가
- 실행은 되지만 비용 반영이 안 되는가
- 추천/대시보드만 늦는가

## 5.4 완화

가능한 경우 아래 우선순위로 완화한다.

1. 장애 확산 차단
2. 핵심 기능 복구
3. 데이터 정합성 복구
4. 부가 기능 복구

## 5.5 종료 조건

- 핵심 기능 정상화
- 에러율 임계치 이하 회복
- 지연/lag 정상 범위 복귀
- 후속 조치 담당자 지정

## 6. 장애 유형별 런북

## 6.1 유형 A: Gateway 5xx 급증

증상

- UI 실행 요청 실패 증가
- `POST /api/executions` 5xx 증가
- 다수 하위 서비스가 정상처럼 보여도 사용자 체감은 전면 장애

우선 확인

1. 최근 Gateway 배포 여부
2. 최근 Gateway 설정 변경 여부
3. Policy/Redis/외부 AI timeout 여부
4. 공통 에러 코드 Top N

즉시 조치

- 직전 안정 버전 롤백 검토
- 외부 의존성 timeout 상향 또는 circuit breaker 완화 검토
- 특정 신규 라우트만 문제면 feature 비활성화

주 담당

- B

지원

- A: 사용자 증상 재현
- C: 하위 소비 지연은 2차 확인

## 6.2 유형 B: 접근 제어 또는 더미 컨텍스트 이상

증상

- 개발/데모 환경에서 예상과 다른 사용자/팀 컨텍스트 적용
- 특정 환경에서 전 요청이 같은 더미 사용자로 집계
- staging 전환 시 접근 정책 공백이 드러남

우선 확인

1. `DEFAULT_USER_ID`, `DEFAULT_TEAM_ID` 등 기본값 설정
2. debug 헤더 허용 범위
3. 환경별 Gateway 설정 차이
4. 하위 서비스가 기대하는 사용자/팀 필드 존재 여부

즉시 조치

- 잘못된 기본 컨텍스트 설정 롤백
- debug 헤더 허용 범위 축소
- 환경별 설정 재정렬

주 담당

- B

지원

- A

## 6.3 유형 C: 정책 차단 오판단

증상

- 정상 요청이 `POLICY_BLOCKED`로 과도하게 차단
- 특정 팀 또는 모델만 실행 불가

우선 확인

1. 최근 정책 변경 여부
2. 평가 입력 필드 누락 여부
3. 정책 우선순위/범위 충돌

즉시 조치

- 최근 정책 변경 롤백
- 잘못된 룰 비활성화
- 영향 팀에 임시 우회 정책 적용 검토

주 담당

- B

지원

- A: UI 에러 노출 확인
- C: 분석용 차단 데이터 제공

## 6.4 유형 D: 비용 반영 지연 또는 실패

증상

- 실행은 성공했지만 대시보드 비용이 0 또는 오래된 값
- `cost.calculated` 이벤트 미생성

우선 확인

1. `usage.tracked` 이벤트 유입 여부
2. Billing consumer 상태
3. 가격표 버전 누락 여부
4. DB 오류 여부

즉시 조치

- consumer 재기동
- 가격표 핫픽스 적용
- 실패 건 재처리 큐 투입

주 담당

- C

지원

- B: upstream event 생성 확인

## 6.5 유형 E: Recommendation 실패

증상

- 추천 API는 200이지만 빈 결과
- 추천 생성 배치 또는 소비기 중단

우선 확인

1. upstream 집계 데이터 존재 여부
2. 추천 생성 스케줄 실행 여부
3. 추천 필터 조건이 과도한지 여부

즉시 조치

- 기존 추천 캐시 유지
- 배치 재실행
- 추천 기능을 일시적으로 비핵심 기능으로 격리

주 담당

- C

지원

- A: 빈 상태 UX 처리

## 6.6 유형 F: UI 핵심 화면 장애

증상

- 카탈로그 미노출
- 실행 버튼 비활성 또는 무한 로딩
- 실행 결과 화면 파싱 오류

우선 확인

1. 최근 UI 배포 여부
2. API 응답 스키마 변경 여부
3. 프론트 런타임 에러 로그
4. CORS 또는 base URL 문제

즉시 조치

- 직전 UI 버전 롤백
- 특정 화면 기능 플래그 비활성화
- 임시 장애 배너 노출

주 담당

- A

지원

- B: API 호환성 확인

## 7. 장애 커뮤니케이션 템플릿

## 7.1 최초 공지

```text
[Incident Open]
시간: 2026-03-20 22:10 KST
등급: Sev-2
증상: 실행 요청 실패율 증가
영향 범위: 전체 사용자 중 약 40%
우선 담당: B
다음 업데이트 예정: 15분 후
```

## 7.2 중간 업데이트

```text
[Incident Update]
현재 파악: Gateway에서 외부 AI timeout 급증
완화 조치: timeout 상향 및 일부 트래픽 제한
남은 영향: 실행 지연 지속, 비용 적재는 정상
다음 업데이트 예정: 15분 후
```

## 7.3 종료 공지

```text
[Incident Resolved]
종료 시간: 2026-03-20 23:05 KST
원인: 외부 AI timeout 설정 회귀
조치: Gateway 롤백 및 설정 수정
후속: 재발 방지 항목 정리 예정
```

## 8. 사후 회고 템플릿

필수 항목

- 장애 요약
- 사용자 영향
- 탐지 방법
- 타임라인
- 근본 원인
- 잘된 점
- 부족했던 점
- 액션 아이템
- 담당자와 기한

## 9. 데이터 정합성 복구 원칙

- Usage 누락은 원본 이벤트 기반 재처리를 우선한다.
- Billing 누락은 가격표 버전과 원본 사용량 메타데이터를 함께 확인한다.
- 수동 수정이 발생하면 반드시 감사 로그 또는 운영 기록을 남긴다.
- Recommendation 데이터는 핵심 결제 데이터가 아니므로 Usage/Billing 복구 후 재생성한다.

## 10. 역할별 즉시 확인 항목

## 10.1 A

- 사용자에게 보이는 증상
- 브라우저 콘솔/네트워크 에러
- 재현 가능한 최소 시나리오
- 임시 우회 가능 여부

## 10.2 B

- Gateway health
- 더미/테스트 컨텍스트 오적용 비율 또는 사용자 식별 누락
- 정책 차단율
- rate limit 차단율
- upstream timeout

## 10.3 C

- Kafka lag
- Usage/Billing consumer 상태
- 가격표 로딩 상태
- 비용 적재 지연
- 추천 생성 상태

## 11. 훈련 시나리오

운영 전 최소 1회 이상 아래를 리허설한다.

- 정책 오판단 시나리오
- 비용 적재 지연 시나리오
- Gateway timeout 시나리오
- UI/API 계약 불일치 시나리오

## 12. 런북 유지 규칙

- 새 장애 유형이 발생하면 이 문서에 반영한다.
- 담당 서비스가 변경되면 역할 표를 갱신한다.
- 분기 1회 이상 알림 임계치와 대응 절차를 점검한다.
